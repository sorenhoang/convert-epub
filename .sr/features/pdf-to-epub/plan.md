# Plan — pdf-to-epub

## Approach

Option A from design.md: a static Vite + TypeScript site with no backend and no React. `pdfjs-dist` extracts positioned text. Pure TypeScript heuristics turn it into a book model. `jszip` writes EPUB 3. The pipeline runs in a Web Worker. The heuristic core is pure functions over plain data, so most tests are Vitest unit tests on JSON or generated-PDF fixtures. Fixture PDFs are generated by `pdf-lib` inside the tests, so they need no binary files. The one exception is the encrypted fixture, which pypdf makes once and which gets committed.

Probed on this machine with Node 22.22, pdfjs-dist 6.5.438, pdf-lib, pypdf 6.18 and Java 21:
- pdf.js emits empty items with height 0, which F-2 must filter.
- Item height equals font size, and fontName is the same id across sizes.
- A pdf-lib PDF has a null outline.
- An encrypted PDF throws `PasswordException` with code 1.
- In Node, pdf.js warns that `standardFontDataUrl` is missing. Text extraction still works.

## Dependencies and order

```
F-1 (writer) ─┐
F-2 (layout) ─┼─> F-3 (cleanup) ─> F-4 (structure) ─┐
F-5 (errors) ─┘                                      ├─> F-6 (pipeline) ─> F-7 (UI)
```

- F-1, F-2 and F-5 are independent and can run in parallel.
- F-3 needs F-2's line model, and F-4 needs F-3's output.
- F-6 joins all of the above, and F-7 needs F-6.
- Sequential order: F-1, F-2, F-3, F-4, F-5, F-6, F-7. The scaffold is part of F-1.

## Risks

| Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|
| Heuristics pass on generated fixtures but fail on real books | High | High | After F-6, run on 2–3 real PDFs the user supplies and add regression fixtures from what breaks |
| epubcheck passes but Kindle still rejects or misrenders | Low | High | Manual Send-to-Kindle check after F-7. This is not automatable |
| pdf.js worker setup differs between Node tests and the Vite browser build | Medium | Medium | Use the legacy build in Node and the `?url` worker import in Vite. F-7 covers the browser path |
| The 10% garbage-text threshold misfires | Medium | Low | Keep it as one named constant and tune it on real books |
| Large PDFs exhaust memory in the browser | Low | Medium | Stream pages one at a time and release each page after extraction. No hard cap in v1 |
| Two-column detection breaks single-column pages with centered text | Medium | Medium | Require both x-clusters to hold at least 30% of the lines before treating a page as two columns |

## Out of scope (v1)

- OCR for scanned PDFs with tesseract.js. Phase 2. v1 shows the scanned-PDF error instead.
- Images, figures and tables.
- Footnotes as EPUB popups. They stay inline as plain paragraphs.
- Sending to Kindle automatically. That needs a server, which this design excludes.
- Cover image generation.
- React and Tailwind. Plain TS was chosen because the user didn't pick a framework.
- Deploy setup on GitHub Pages or Vercel. It is a one-line follow-up once F-7 passes.

## Implementation notes (implement all, 2026-11-02)

- **F-2 deviation from the acceptance wording.** Paragraph gaps use the lower quartile of same-size line steps, computed per font size, not the page median. The median fails on block-paragraph layouts where blank-line gaps outnumber normal line steps. That failure showed up in the F-6 fixture. All locked F-2 tests still pass. The decision is listed for the user.
- **Review.** One independent review covered all items instead of one per item, because the code is a single new pipeline. It found 6 critical issues and an unproven goal-4. All were fixed, with new tests in `test/review-fixes.test.ts`. Existing test files were not edited after their first RED run.
- **pdf.js in Node.** Vitest aliases `pdfjs-dist` to the legacy build because Node 22 lacks `Promise.try`. The browser uses the modern build.
